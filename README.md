# Тапшырма

Конструктор технических заданий на информационные системы для государственных органов
Кыргызской Республики. Мастер-анкета собирает машиночитаемую модель документа, из которой
выводится техническое задание по структуре ГОСТ 34.602 и которая проверяется движком правил
на соответствие требованиям законодательства о государственных закупках.

Сделаны этапы 2–4, 6 и 7–8 дорожной карты. Что есть и чего нет — в конце файла.

## Развёртывание

Публикация на Netlify описана в [DEPLOY.md](DEPLOY.md): сборку делает Netlify
в облаке, база — Neon, схема применяется через браузер. **Node на машине
разработчика для этого не нужен.**

## Запуск на localhost

Всё уже установлено в домашнюю папку, без sudo и без изменений в системе:

- Node 20.20.2 — `~/.local/opt/node-v20.20.2-darwin-x64`, ссылки в `~/.local/bin`
- PostgreSQL 16.15 — бинарники из Postgres.app в `~/.local/opt/Postgres.app`,
  кластер в `~/.local/var/postgres-tapshyrma`, порт 5433

```sh
cd ~/tapshyrma
./start.sh
```

Откройте <http://localhost:3000> и войдите: `drafter@example.kg` / `tapshyrma`.

Остановить: `Ctrl+C` в окне приложения, затем `./stop.sh` для базы.

Если понадобится пересоздать базу с нуля:

```sh
npm run db:push    # схема из db/schema.ts
npm run db:seed    # орган, пользователь и демонстрационный документ
```

Полезное:

```sh
npm run check       # самопроверки движка правил и экспорта, база не нужна
npm run typecheck   # проверка типов
npm run smoke       # сквозная проверка интерфейса в браузере (нужен puppeteer)
npm run db:studio   # веб-интерфейс к базе
```

Браузерная проверка ставится отдельно и один раз:

```sh
npm install --no-save puppeteer
npm run dev            # в другом окне
npm run smoke
```

Её стоит гонять и по сетевому адресу — часть ошибок видна только там:

```sh
BASE=http://10.0.0.187:3000 npm run smoke
```

> Почему это важно: `crypto.randomUUID` работает на `http://localhost`, но
> отсутствует по адресу вида `http://10.0.0.187:3000` — последний не считается
> защищённым контекстом. Из-за этого кнопки «Добавить» молча не работали,
> и ни проверка типов, ни самопроверки такого не ловят.

## Устройство

Конвейер из плана продукта, шесть стадий:

```
Анкета  →  Модель ТЗ  →  AI-блоки  →  Рендер ГОСТ  →  Аудит правил  →  Экспорт
  01          02            03            04              05             06
  ✓           ✓             —             ✓               ✓              ✓
```

| Файл | Роль |
| --- | --- |
| `lib/tz/model.ts` | Модель ТЗ: типы и zod-схема. Единственное определение того, что такое документ. |
| `lib/tz/derive.ts` | Компилятор: коды требований, нумерация этапов, сроки, перечень документации, раздел 9. Чистая функция. |
| `lib/questionnaire/steps.ts` | Анкета целиком, декларативно. Новый вопрос добавляется здесь и нигде больше. |
| `lib/rules/rules.ts` | Реестр правил R-01…R-14 — движок проверок. |
| `lib/rules/dictionaries.ts` | Словари торговых марок и неизмеримых формулировок. |
| `lib/rules/engine.ts` | Прогон документа через реестр, подсчёт блокирующих и необоснованных замечаний. |
| `lib/tz/vocabulary.ts` | Формулировки для кодов модели. Общие для экрана и для DOCX, чтобы два рендерера не разошлись. |
| `lib/export/docx.ts` | Генератор .docx: те же девять разделов, что в превью. |
| `lib/export/zip.ts` | Писатель ZIP без зависимостей — .docx это ZIP с XML внутри. |
| `lib/reference/legal-acts.ts` | Справочник НПА. Единственный источник ссылок на нормы во всём продукте. |
| `components/Preview.tsx` | Рендер документа по ГОСТ 34.602. Ни одного редактируемого поля: документ выводится, а не пишется. |
| `db/schema.ts` | Организации, пользователи, документы, версии со снимком модели в JSONB. |

Три правила, на которых держится продукт:

1. **Ссылки на нормы не пишутся руками и не генерируются моделью.** Раздел 9 собирается
   в `sourcesFor()` только из справочника, по фактически задействованным ответам анкеты.
2. **Решение «выпускать документ или нет» принимает детерминированный движок**, а не языковая
   модель. `lib/rules/engine.ts` — чистая синхронная функция без сети и без базы.
3. **Версия документа не перезаписывается.** Каждое сохранение добавляет строку в
   `document_versions` со снимком модели целиком, включая обоснования замечаний.

## Движок проверок

Блокирующее замечание не даёт передать документ на утверждение и обосновать его нельзя —
только устранить. Предупреждение требует от составителя текста обоснования, который
сохраняется внутри документа (`compliance.justifications`) и попадает в снимок версии:
при разборе спорного ТЗ видно не только требование, но и чем составитель объяснил замечание.

| Код | Проверка | Основание | Тип |
| --- | --- | --- | --- |
| R-01 | Торговые марки и наименования производителей | Закон № 27 | блок / предупр. при оговорке «или эквивалент» |
| R-02 | Неизмеримые формулировки требований | Закон № 27 | предупр. |
| R-03 | Полнота обязательных разделов | ГОСТ 34.602 | блок |
| R-04 | Код ОКГЗ указан и соответствует предмету | Закон № 27 | блок / предупр. при расхождении |
| R-05 | Критерий приёмки у каждого требования | ГОСТ 34.602 | предупр. |
| R-06 | Блок требований к обработке персональных данных | Закон № 58 | блок |
| R-07 | Требования к защите информации | ПП КР о защите БД ГИС | блок |
| R-08 | Межведомственный обмен через «Түндүк» | Регламент «Түндүк» | предупр. |
| R-09 | Передача исходного кода и исключительных прав | ГК КР | блок |
| R-10 | Государственный и официальный языки интерфейса | О государственном языке | блок |
| R-11 | Квалификационные требования не ограничивают конкуренцию | Закон № 27 | **не реализовано** |
| R-12 | Гарантийный срок и техническая поддержка | ГК КР | предупр. |
| R-13 | Сроки этапов заданы и непротиворечивы | — | предупр. |
| R-14 | Ссылки на НПА существуют и подтверждены | — | блок / предупр. при `unverified` |

R-11 остаётся в реестре с `implemented: false`, потому что в модели ещё нет раздела
квалификационных требований. Панель аудита показывает такие правила отдельным списком —
иначе непонятно, чего документ не проверил.

Словари в `lib/rules/dictionaries.ts` заведомо неполные: они наполняются из корпуса реальных
ТЗ на неделе 1 плана. R-01 ловит частые случаи, а не все, и не заменяет вычитку юристом.

## Экспорт в .docx

`lib/export/docx.ts` собирает документ прямо в OOXML, `lib/export/zip.ts` упаковывает
части в ZIP. Внешних библиотек нет намеренно: код писался на машине без npm, и
зависимость, которую нельзя ни установить, ни проверить, была бы хуже сотни строк
своего кода. Записи кладутся без сжатия — Word такие архивы открывает, а отсутствие
deflate убирает целый класс ошибок.

Два свойства, на которые стоит обратить внимание:

- **Экспортируется последняя сохранённая версия**, а не содержимое мастера. Файл уходит
  из системы и может попасть в конкурсную документацию, поэтому обязан соответствовать
  зафиксированной версии, у которой есть автор и время.
- **Сборка детерминирована**: отметка времени внутри архива фиксирована, поэтому две
  выгрузки одной версии дают побайтово одинаковый файл и сравнимы между собой.

`npm run check:docx` собирает документ, **разбирает получившийся архив обратно** и
сверяет контрольные суммы каждой записи — самая частая ошибка в рукописном ZIP
это сдвиг смещений, при котором файл выглядит правдоподобно и не открывается.
Готовый файл кладётся в `./out`; открыть его в Word — единственная настоящая проверка.

Чего в экспорте пока нет: фирменного бланка органа (нужен .docx-шаблон самого органа),
колонтитулов с номерами страниц и PDF.

## Что уже работает

- Вход, организация, роли в схеме базы.
- Мастер-анкета из 11 шагов с ветвлением на двух уровнях: шаг целиком и отдельное поле.
- Модель ТЗ и её компиляция: коды `ФТ-01…`, этапы `Э-1…`, календарные сроки,
  таблица соответствия требований и критериев приёмки в разделе 6.
- Живой документ по ГОСТ 34.602 рядом с анкетой, с честной пометкой незаполненных мест.
- Аудит по 13 правилам, пересчёт на каждый ввод, обоснования предупреждений.
- Экспорт в .docx: A4, Times New Roman 12 пт, поля 3 см слева — открывается в Word.
- Версионирование: каждое сохранение — новая версия со снимком модели.

## Чего ещё нет

| Не сделано | Этап плана |
| --- | --- |
| Вывод на фирменный бланк органа и экспорт в PDF | 5–6 |
| Справочники НПА и ОКГЗ в базе с админкой для юриста | 7–8 |
| Слой AI: генерация описательных разделов, вычитка | 9–10 |
| Маршрут согласования, сравнение версий, аудит-лог | 11–12 |
| Правило R-11 и раздел квалификационных требований | после корпуса |
| Импорт существующего ТЗ из DOCX | после пилота |

Статус «Утверждён» пока не выставляется из интерфейса: панель аудита считает `canApprove`,
но сам маршрут согласования появляется на этапе 11. Сохранение версии блокирующие замечания
не запрещают — черновик можно сохранять любым.

## Открытые вопросы

Помечены в `lib/reference/legal-acts.ts` статусом `unverified` и закрываются на неделе 1:
редакция и статус применения ГОСТ 34.602, 19.201 и 34.201 в КР, реквизиты регламента
«Түндүк» и законодательства о государственном языке. Правило R-14 показывает такие ссылки
предупреждением в каждом документе, который их задействовал, — до подтверждения юристом
эти нормы не должны попадать в блокирующие проверки.

Отдельно — решение по хостингу продакшена (раздел 07 плана продукта). До него архитектура
держится переносимой: обычный Node, PostgreSQL, никаких API конкретной платформы.
